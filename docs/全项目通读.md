# 第一部分：一条请求的完整旅程

**拿 `GET /books/9787115428028` 走一遍。这是整个项目最短的一条完整路径，也是最有代表性的一条。**

## ① 到 Nginx 之前

**浏览器发的是 `http://你的域名/books/9787115428028`（不带端口号）。**

**Nginx（`nginx.conf`）收到，按 `proxy_pass` 转给应用容器。**

**⚠️ 这里有个细节:如果这是 WebSocket 请求（`/ws`），Nginx 必须带上**升级头**才能转过去 —— `proxy_http_version 1.1`、`Upgrade`、`Connection: upgrade` 三个都要。**这就是第 13 周埋下、第 15 周兑现的那个伏笔。**

## ② 进到应用

**uvicorn 收到请求，交给 ASGI 应用 —— 也就是 `main.py` 里那个 `app` 对象。**

**请求从最外层往里走，依次经过:**

| 顺序 | 是谁 | 干什么 |
| --- | --- | --- |
| 1 | **`ServerErrorMiddleware`** | **兜住所有没人处理的异常** —— 就是它把控制权交给你的 500 处理器 |
| 2 | **`add_request_id`** | **生成本次请求的编号**（或读上游传来的），写进请求上下文 |
| 3 | **`log_requests`** | **记"进来"一条**，然后 `call_next`，回来再记"出去"一条 |
| 4 | **CORS 中间件** | 跨域放行 |
| 5 | **`ExceptionMiddleware`** | **把你的业务异常翻译成 HTTP 响应** |

**⚠️ 顺序很重要 —— 而且它在 `main.py` 里是"**后注册的在外层**"（add_request_id 在 log_requests 之后注册，所以先跑）。**

**这就是为什么给本次请求生成的编号，在日志中间件里已经拿得到了。**

## ③ 找到端点

**路由匹配到 `api/routers/book.py` 里的 `get_book` 函数。**

## ④ 解析依赖（这一步最容易忽略，但它是最关键的）

**FastAPI 在调用端点函数**之前**，先把它的依赖全部算出来。顺序是:**

| 顺序 | 依赖 | 干什么 |
| --- | --- | --- |
| 1 | **`books_rate_limit`**（路由器级） | **按用户限流** —— 去 Redis 自增一个计数器，超了抛 429 |
| 2 | **`get_caller`**（路由器级） | **认人** —— 从请求头取令牌、解开、去数据库查这个用户还在不在 |
| 3 | **`CurrentBookDep`**（参数级） | **按 ISBN 取书** —— 走 `BookService`，也就是下面那一整条 |

**⚠️ 路由器级的依赖排在最前面** —— 这是第 13 周 Day 6 讲过的:**路由器级的依赖是第一道关，谁都绕不过去。**（也正是它，曾经让注册接口被要求登录。）

## ⑤ 认人那一步往下

**`get_caller` 里面是这么一条链:**

```
从请求头取令牌  →  oauth2_scheme
解开令牌        →  decode_access_token（用的是 SECRET_KEY 和 ALGORITHM）
拿到用户名      →  payload["sub"]
去数据库查这个人 →  UserService.get_user  →  UserRepository.get
查不到就 401    →  抛 InvalidCredentials
```

**⚠️ 注意 `deps.py` 里那个 `oauth2_scheme` —— 它**只认请求头**。所以浏览器的 WebSocket 用不了它（浏览器不让自定义请求头），第 13 周的令牌才走了网址参数。**

## ⑥ 限流那一步往下

**`books_rate_limit` 是"按用户限流"的工厂产出的。它拿到用户名之后，把活交给 `_check_limit`:**

```
先确保计数器存在，并且带着过期时间   →  cache.set(key, 0, ex=window, nx=True)
然后原子自增，拿到"这是第几次"       →  cache.incr(key)
超了就抛 429                        →  HTTPException(429)
Redis 连不上就放行（fail-open）      →  except RedisUnavailable: 记一条 WARNING 然后返回
```

**⚠️ "先设 TTL 再自增"这个顺序不是随意的 —— 它保证**不会留下一个永不过期的计数器**（那样这个 IP 就被永久封禁了）。**

## ⑦ 取书那一步往下 —— 穿过四层

**`CurrentBookDep` → `get_current_book` → `BookService.get_book`。到这里开始进入业务层:**

```
先去缓存拿                  →  _cache_get(key)   →  Redis GET
拿到了就返回                →  （顺带说明:缓存里可能存着"这本书不存在"这个结论）
没拿到就去数据库查           →  self.repo.get(isbn)  →  仓储层
查到了就写回缓存            →  _cache_set(key, ..., ex=CACHE_TTL)
```

**仓储层最后落到一条 SQL:**

```
select(Book).where(Book.isbn == isbn)  →  交给 Postgres
```

**⚠️ 缓存的三个包装（读 / 写 / 删）里都有同一个 `except RedisUnavailable` —— 那是"缓存是加速器，不是必需品"这句话在代码里的样子。**

## ⑧ 回来

**书是一个字典 `dict`。FastAPI 拿它去套响应模型 `BookResponse` —— 这一步会**过滤掉**不该给外面看的字段（比如 `internal_note`）。**

**然后原路返回:Nginx → 浏览器。**

**同时 `log_requests` 记下"出去"那一条，带着**和进来时同一个**请求编号。**

## `src/my_fastapi_project/` —— 主包

### 顶层

| 文件 | 它在做什么 |
| --- | --- |
| **`main.py`** | **应用的装配车间。** 它做六件事:造 `app`、定义 `lifespan`、装两个中间件、装 CORS、注册所有路由、注册异常处理器 |
| **`__init__.py`** | **空的** —— 从第 14 周起，这个包被导入时**不该有任何副作用** |

**关于 `main.py` 里那个 `lifespan`:** 它是"应用的一生"。`yield` 之前是启动（起 Redis 订阅任务），`yield` 之后是关闭（停订阅 → 关 Redis → 关数据库引擎）。**关闭的顺序和启动反着来。**

### `core/` —— 基础设施

**这一层的共同点:它们**不依赖**业务，业务依赖它们。**

| 文件 | 它在做什么 | 关键名字 |
| --- | --- | --- |
| **`config.py`** | **所有配置项的唯一定义处。** 值从 `.env` 来，代码里只读 | `Settings`、`get_settings` |
| **`db.py`** | **数据库引擎和会话工厂** | `engine`、`SessionFactory`、`Base` |
| **`redis.py`** | **Redis 客户端**，以及"哪些异常算连不上" | `redis_client`、`RedisUnavailable` |
| **`security.py`** | **密码和令牌的两件事** —— 哈希/校验、签发/解开 | `hash_password`、`verify_password`、`create_access_token`、`decode_access_token` |
| **`roles.py`** | **两个角色常量** | `ROLE_USER`、`ROLE_ADMIN` |
| **`exceptions.py`** | **业务异常体系。** 一个基类 + 一堆具体异常，每个自带 HTTP 状态码 | `BusinessError` 及其子类 |
| **`errors.py`** | **四个异常处理器** —— 把异常翻译成统一的 JSON 响应 | `http_exception_handler`、`validation_exception_handler`、`unhandled_exception_handler`、`business_error_handler` |
| **`logging_config.py`** | **日志的全部配置** —— 格式、脱敏、请求编号注入 | `setup_logging`、`RedactingFormatter`、`request_id_var` |

**三个值得记住的细节:**

- **`db.py` 里的池参数**（`pool_size` 等）是从配置来的 —— 第 16 周压测时才发现它们该能调
- **`errors.py` 里只有 500 和"认证失败"记日志。** 404 之类**故意不记** —— 那是日志洪水
- **`logging_config.py` 里的 `RedactingFormatter`** 负责把令牌从日志里抹掉。**这是第 13 周欠下、第 14 周还的账**

### `models/` —— 数据库表

| 文件 | 表 | 关键点 |
| --- | --- | --- |
| **`user.py`** | `users` | 主键是 `username`；`email` 唯一；`profile` 是 JSON 列 |
| **`book.py`** | `books` | 主键是 `isbn`；`internal_note` 是不外露的字段 |
| **`borrow_record.py`** | `borrow_records` | **两条外键**指向用户和书；两个时间列都是**带时区**的 |
| **`__init__.py`** | —— | **它的作用是"让三个模型都被导入"** —— 否则 Alembic 看不见它们 |

**⚠️ `borrow_records` 是"借阅这件事"本身。** 第 11 周特意没有往 `books` 上加一列 —— 因为一本书会被借很多次，**那是"一对多"**。

### `schemas/` —— 接口的输入输出形状

| 文件 | 管什么 |
| --- | --- |
| **`user.py`** | 用户的新建 / 更新 / 返回 / 改密码。**返回模型里没有密码字段** |
| **`book.py`** | 图书的新建 / 更新 / 返回。**返回模型里没有 `internal_note`** |
| **`token.py`** | 登录成功后返回什么（`access_token` + `token_type`） |
| **`borrow.py`** | 借阅记录的返回形状（**不带用户名** —— 那是调用者自己） |

**这一层的意义:** Pydantic 模型是**边界**。外面来的数据先过它，里面出去的数据也过它。**"不该给的字段"，靠它挡住。**

### `repositories/` —— 只跟数据库说话

| 文件 | 管什么 |
| --- | --- |
| **`user_repo.py`** | 用户的增删改查、按邮箱查重 |
| **`book_repo.py`** | 图书的增删改查，**外加两条"原子库存操作"** |
| **`borrow_repo.py`** | 借阅记录的创建、关闭、按人查（**带关联加载**） |

**两条值得单独说的:**

- **`book_repo.py` 里的"减库存"是一条带条件的 `UPDATE`**（`WHERE stock > 0`）—— **它把"检查"和"扣减"压成了一次操作。** 这是第 11 周解决超卖的办法
- **`borrow_repo.py` 里"按人查记录"用了预加载** —— 因为每条记录要带上书名，而**异步下不能懒加载**（第 11 周那个坑）

### `services/` —— 业务规则住在这儿

| 文件 | 管什么 |
| --- | --- |
| **`user_service.py`** | 注册（查重 + 哈希）、登录校验、改密码、增删改查。**所有密码相关的操作都在线程里跑** |
| **`book_service.py`** | 图书的增删改查、**借书、还书**，以及**缓存的读写与失效** |
| **`borrow_service.py`** | **只有一件事:列出"我的"借阅记录** |

**三处值得记住的:**

- **`user_service.py` 里的 `asyncio.to_thread`** —— bcrypt 是 CPU 密集的，丢到线程里才不会卡住整个事件循环
- **`book_service.py` 里的 `_cache_get` / `_cache_set` / `_invalidate`** —— **缓存的三道口子都收在这三个方法里。** 降级、脱敏、日志都因此只写一遍
- **`book_service.py` 里的 `borrow`** —— **它先扣库存再写记录，两次提交。** 这是项目里记录在案的一处债（README 里有）

### `api/` —— 接口层

| 文件 | 它在做什么 |
| --- | --- |
| **`deps.py`** | **依赖的总仓库。** 会话、Redis、仓储、服务、调用者、分页、限流、权限 —— 全在这儿 |
| **`ws_manager.py`** | **在线名单。** 谁连着、各开了几条。**它住在进程内存里** |
| **`ws_bus.py`** | **跨进程广播。** 一个负责发，一个负责收，中间是 Redis 的发布订阅 |
| **`routers/`** | 六个路由模块:认证、用户、图书、借阅、健康检查、WebSocket |

**`deps.py` 是这个项目里最"重"的文件，值得单独理解。它里面有五类东西:**

| 类别 | 例子 | 干什么 |
| --- | --- | --- |
| **会话与连接** | `get_session`、`get_redis` | 提供数据库会话和 Redis 客户端 |
| **业务对象** | `get_user_service`、`get_book_service` | **把仓储和缓存组装成服务** |
| **认人** | `get_caller` | 从令牌解出调用者 |
| **限流** | `_check_limit` + 两个工厂 | 按 IP / 按用户限流 |
| **授权** | `require_role`、`require_self_or_admin`、`require_not_self` | 三类权限判断 |

**⚠️ 关于限流那两个工厂，有一个反直觉的地方:** `rate_limiter` 是"按 IP"，`user_rate_limiter` 是"按用户"。**后者要求令牌，所以它**不能**挂在公开接口上。**这就是第 13 周那次 401 事故的根源。

| **13** | **服务器要能主动说话** | **`api/ws_manager.py`、`api/ws_bus.py`、`api/routers/ws.py`** |
| **14** | **出事了要看得见** | **`core/logging_config.py`、以及散落各处的 `logger.warning`** |
| **15** | **换台机器也能跑** | **`Dockerfile`、`compose.yaml`、`nginx.conf`、`alembic/`** |
| **16** | 它到底能扛多少 | `scripts/locustfile.py`、`docs/压测报告.md` |

**这张表里有五处是"整门课的主线"，值得单独记:**

1. **第 4 周的分层** —— 后面每一周都在往这条线上加东西，从没破过
2. **第 7 周的测试** —— 它救了两次命（第 13 周的 401 事故、第 14 周那个跑旧代码的问题）
3. **第 9 周的异步** —— 它决定了第 11 周那个"异步下不能懒加载"的坑
4. **第 12 到 13 周的那条线** —— **"状态住在进程里，多个进程就各说各话。"** 先是计数，后是连接名单
5. **第 14 到 15 周的那条线** —— **"降级解决了服务还能用，但制造了故障看不见。"** 先是日志，后是部署

# 第四部分：这个项目现在的边界和债

**这一节是最值得留着的一节。** 它写的是"**我知道它哪里还不够好**"。

## 记录在案的债

| 债 | 在哪儿 | 什么后果 |
| --- | --- | --- |
| **`BookService.borrow` 分两次提交** | `services/book_service.py` | 扣完库存、还没写记录时崩溃 → **少一本书，没有记录** |
| **`scripts/db_check.py` 会报错** | 那段 SQLite 专用的 `PRAGMA` 检查 | 换 Postgres 之后跑不了 |
| **`scripts/init_db.py` 和 Alembic 是两套** | `create_all` vs 迁移 | 用了 Alembic 之后，**改表结构不能再靠 `create_all`** |
| **`/msg` 私聊不跨进程** | `ws_manager.send_to_user` | 多 worker 下私聊是坏的 |
| **Redis 挂了会同时降级缓存和限流** | `book_service` + `_check_limit` | **缓存走数据库（变慢）**加上**限流全放行（不设防）** |

## 没做的事（不是债，是边界）

| 没做 | 为什么现在可以不做 |
| --- | --- |
| **HTTPS** | 需要真域名 + 公网可达 —— 留给第 17 周 |
| **心跳与断线重连** | WebSocket 长连接的保活机制，真实项目要 |
| **多副本 / 负载均衡** | 现在只有一台 NAS |
| **监控报警** | 日志有了，但"出事时主动通知人"没有 |
| **数据库索引调优** | 数据量太小，看不出来 |

## 这个项目的"数字边界"

**从第 16 周的压测报告里能得到几条:**

- **它在一台自组装 NAS 上、跑 4 个 worker、只有几十条数据时，能扛住 20 个并发**
- **瓶颈通常在 ______（照你的报告填）**
- **条件一变（数据变多、并发变高、压测机换成别的），结论就可能不成立**

**⚠️ 最后这一句是整份文档里最重要的一句:**

> **"我知道我的结论在什么条件下成立。"**
>
> **这句话比任何一个数字都值钱。**
