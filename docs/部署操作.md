## 三、让它一直在（后台常驻模式）

**上面那种前台跑法，SSH 一关就没了，NAS 重启也不会自己起来。**

**要常驻，换成这一条 —— 在 NAS 的 SSH 窗口：**

```bash
docker run -d --name myapp --restart unless-stopped -p 8000:8000 --env-file .env myapp:0.1
```

**和前台版比，多了三样、少了 `--rm`：**

| 参数 | 意思 |
| --- | --- |
| **`-d`** | **后台跑** —— SSH 关了它还在 |
| **`--name myapp`** | **给它起名字**，以后用名字指它 |
| **`--restart unless-stopped`** | **NAS 重启后自动起来** |
| **去掉 `--rm`** | **`--rm` 和 `--restart` 不能一起用**（Docker 会报冲突） |

**相关的三条命令，都在 NAS 的 SSH 窗口：**

```bash
docker logs -f myapp
```
**看日志。`-f` 是"跟着滚"。按 `Ctrl+C` 只是停止看，容器不受影响。**

```bash
docker stop myapp
```
**停掉它。**

```bash
docker rm myapp
```
**彻底删掉。** —— **注意：下次重新 `docker run --name myapp` 之前，必须先删掉旧的，否则会报名字冲突。**

## 六、Dockerfile 的现状（Day 15.2 之后）

**文件位置：仓库根目录的 `Dockerfile`** —— **必须是大写 `D` 开头。**

**结构记三句话：**

1. **第一个 `FROM python:3.11-slim AS builder`** —— 依赖和项目都在这里装好
2. **先 `COPY pyproject.toml uv.lock ./` 再 `RUN uv sync --no-install-project`** —— 这样**改代码不会触发重装依赖**
3. **第二个 `FROM`（最终镜像）** —— 只从 builder 搬 `/app`，构建垃圾全留在 builder 里

**现在的体积和时间（Day 15.2 实测）：**

| | 单阶段 | 多阶段 |
| --- | --- | --- |
| **镜像大小** | **314MB** | **226MB**（省 88MB） |
| **改一行代码后重建** | 重装所有依赖 | **装依赖那步显示 `CACHED`**，约 23 秒 |

**88MB 省在哪：** 55.7MB 是 uv 这个程序本身（只在 builder 里用），剩下的约 32MB 是 uv 的下载缓存和中间产物。

**⚠️ 要加一个"构建需要的新文件"时，记得在 Dockerfile 里补一行 `COPY`。**

**放在**装依赖那步之后**（和 `COPY README.md ./`、`COPY src ./src` 在一起）—— 放在前面会让改这个文件就重装依赖。**

## 七、遇到过的问题（留个记录）

| 现象 | 原因 | 怎么解决 |
| --- | --- | --- |
| `docker build` 卡在 `Sending build context` 很久 | **`.venv` 被一起打包了** | 检查 `.dockerignore` 第一行是不是 `.venv` |
| 容器日志里出现 `Installed 6 packages` | **`uv run` 默认会装 dev 依赖** | 改成多阶段构建 + 直接调 `uvicorn`（Day 15.2） |
| `permission denied` 跑 docker | 用户不在 docker 组 | 命令前加 `sudo`，或用 `usermod -aG docker` |
| 浏览器 404 | 访问的路径项目里没有 | 用 `/health` 或 `/docs` |
| **构建"成功"了，但用的是旧内容** | **文件名是小写 `dockerfile`** —— Windows 看不出来，**Linux/Docker 认的是大写 `Dockerfile`**，而 git 认得的是另一个名字 | 用 `git mv dockerfile tmp_dockerfile` + `git mv tmp_dockerfile Dockerfile` 改成大写 |
| **`failed to open file /app/README.md`** | **`uv sync` 打包项目时要读 `README.md`**（`pyproject.toml` 里写着 `readme = "README.md"`），而 Dockerfile 没 COPY 它 | Dockerfile 里加 `COPY README.md ./`，**放在装依赖之后** |
| `git status` 说 "up to date"，但其实没拉到东西 | **它比的是本地的 `origin/main` 记录** —— pull 被打断时那个记录不会更新 | 先 `git fetch origin`，再看 `git status`。**或者直接 `grep` 文件内容验证** |

**关于文件名那条，有一个值得记住的点：**

> **Docker 其实**也认小写的 `dockerfile`** —— 所以它不报错，只是构建了一个 git 从来没更新过的文件。**
>
> **不报错的错，永远比报错的错难查。**

**还有一条同样性质的:**

| 现象 | 原因 | 怎么解决 |
| --- | --- | --- |
| `docker run` 报 `address already in use`（绑定端口失败） | **宿主机那个端口已经被别人占了** | 换一个宿主机端口（`-p 15432:5432`），**或者查出占用者** |
| 换 Postgres 后，凡是**写时间**的接口都报 `asyncpg ... DataError` | **`Mapped[datetime]` 默认是不带时区的列**（`TIMESTAMP WITHOUT TIME ZONE`），而代码给的是 `datetime.now(UTC)`（带时区） | 列要写成 `mapped_column(DateTime(timezone=True))` |
| 某个断言在 Postgres 上失败，说"应该是字符串" | **SQLite 把 JSON 存成 TEXT，Postgres 有真正的 JSON 列** —— asyncpg 会自动解码成 dict | 删掉那句"实现细节"断言，或者改成断言 dict |
| `VARCHAR(n)` 限制了长度 | **SQLite 完全忽略长度限制，Postgres 严格按 n 截断/报错** | 检查字段长度够不够（比如 `String(13)` 装 13 位 ISBN） |

**这三条是同一个主题:**

> **换数据库不只是"换个连接串"。**
> **两个数据库的"性格"不一样 —— 类型严格程度、有没有时区、怎么存 JSON、管不管长度。**
>
> **测试跑在一个数据库上、应用跑在另一个上，这些差异你永远看不到。** 这也是第 15 周 Day 4 要把测试也搬过来的原因。

## 八、Postgres（Day 15.3 起）

### 起容器（只做一次）

**在 NAS 的 SSH 窗口：**

```bash
docker run -d \
  --name pg \
  --restart unless-stopped \
  -e POSTGRES_PASSWORD=你的密码 \
  -e POSTGRES_DB=library \
  -v pg-data:/var/lib/postgresql/data \
  -p 15432:5432 \
  postgres:16
```

**每个参数的意思：**

| 参数 | 意思 |
| --- | --- |
| `-e POSTGRES_PASSWORD` | **必须给** —— 不给它不启动 |
| `-e POSTGRES_DB=library` | 顺便建一个叫 `library` 的库 |
| `-v pg-data:/var/lib/postgresql/data` | **数据存到容器外面** —— 容器删了数据还在 |
| `-p 15432:5432` | **NAS 的 15432 → 容器的 5432** |
| `--restart unless-stopped` | NAS 重启后自动起来 |

**（用户名默认是 `postgres`，不用设。）**

### ⚠️ 为什么是 15432 而不是 5432

**第一次试着用 `-p 5432:5432` 时失败了：**

```
failed to bind host port for 0.0.0.0:5432:...: address already in use
```

**而 `docker ps` 里没有任何容器用 5432 —— 说明占用者是**NAS 系统自己**（很多 NAS 系统内部用 Postgres 存元数据）。**

**别去停它。改自己的端口就完了。**

**查一下占用者（可选）：**

```bash
sudo ss -tlnp | grep 5432
```
```bash
sudo netstat -tlnp | grep 5432
```

### 验证它活着

**在 NAS 的 SSH 窗口：**

```bash
docker ps
```
```bash
docker logs pg
```
**等到 `database system is ready to accept connections`。**

```bash
docker exec -it pg psql -U postgres -d library -c "select 1"
```
**看到一张 `1` 的小表格 → 通了。**

### 建表 + 看数据

**在你自己的电脑（PowerShell）：**

```powershell
uv run python scripts/init_db.py
```

**它的作用是连上数据库、把所有表建出来、再打印一遍内容。** 看到表名和记录数就说明整条链路通了。

**（注意 `scripts/db_check.py` 里有一段 SQLite 专用的 `PRAGMA` 检查 —— 换成 Postgres 之后它会报错，别跑它。）**

### 连接串的写法

```ini
DATABASE_URL=postgresql+asyncpg://postgres:<密码>@192.168.222.233:15432/library
```

**`+asyncpg` 不能少** —— 不写的话 SQLAlchemy 会去找一个叫 `psycopg2` 的**同步**驱动，你没装，直接报错。

## 九、Compose 的日常用法（Day 15.5 起）

**配置文件：仓库根目录的 `compose.yaml`。** 三个服务：`app`、`pg`、`redis`。

**全部命令都在 NAS 的 SSH 窗口、项目目录里跑：**

```bash
cd ~/FastAPI_learning
```

### 日常流程（改完代码之后）

```bash
git pull
docker compose up -d --build
```

**`-d` 后台跑，`--build` 先把镜像重建一遍。** 一条命令把三个服务都拉起来。

**（对比之前:手动 `docker build` + `docker run` + 记一堆参数。**现在这些都在 `compose.yaml` 里了。**）**

### 最常用的几条

```bash
docker compose ps
```
**三个服务的状态。** 要看到 `pg` 和 `redis` 是 `(healthy)`。

```bash
docker compose logs -f app
```
**跟应用的日志。** `Ctrl+C` 只是停止看，容器不受影响。

```bash
docker compose stop redis
```
**停掉某一个服务**（比如做降级演练）。**再 `docker compose start redis` 恢复。**

```bash
docker compose restart app
```
**只重启应用。**

```bash
docker compose down
```
**停掉并删掉所有容器**（volumes 保留，数据还在）。

### ⚠️ 一个危险的命令

```bash
docker compose down -v
```

**`-v` 会把 volumes 一起删掉 —— 你的 `pg-data` 就在里面，数据库会被清空。**

**这两个命令长得太像了。敲之前看清楚有没有那个 `-v`。**

### 容器之间怎么互相找到

**`compose.yaml` 里的服务名，就是容器里的主机名。**

- 应用连数据库用 `pg:5432`（不是 NAS 的 IP）
- 应用连 Redis 用 `redis:6379`

**所以 `compose.yaml` 里一个宿主机地址都没有** —— 换台机器、换个 IP，这个文件一个字不用改。

### `.env` 的双重身份

**`.env` 同时被两方读:**

| 谁读 | 用来干什么 |
| --- | --- |
| **Compose** | 做 `${POSTGRES_PASSWORD}` 这种变量替换 |
| **应用**（`compose.yaml` 里的 `env_file:`） | 传进容器当环境变量 |

**而 `compose.yaml` 里的 `environment:` 会**覆盖** `env_file` 传进去的同名项。**

**所以 `.env` 里的 `DATABASE_URL`（指向 NAS 的 IP）给你本机跑测试用；容器里那份被覆盖成 `pg:5432`。**

### 一个坑：`.env` 里有应用不认识的变量

**`.env` 里加了 `POSTGRES_PASSWORD` 之后，应用启动会报:**

```
pydantic_core.ValidationError: 1 validation error for Settings
postgres_password
  Extra inputs are not permitted [type=extra_forbidden, ...]
```

**因为 `Settings` 默认不允许多余的配置项。**

**解决：`core/config.py` 的 `model_config` 里加 `extra="ignore"`。**

**为什么可以放心加：真正要防的是"少了一个必需变量"（`DATABASE_URL`、`SECRET_KEY` 没有默认值，缺了照样报错），不是"多了一个部署工具的变量"。**

## 十、Alembic 的日常用法（Day 15.6 起）

**配置文件：`alembic.ini` + `alembic/env.py`。迁移脚本放在 `alembic/versions/`。**

**⚠️ `alembic/versions/` 里的 `.py` 文件**必须进 git** —— 那是数据库结构的变更历史，不是生成物。**

**全部命令在你自己的电脑（PowerShell）跑：**

```powershell
uv run alembic current
```
**当前数据库停在哪个版本。**

```powershell
uv run alembic history
```
**所有迁移的顺序。**

```powershell
uv run alembic revision --autogenerate -m "这次改了什么"
```
**对比"模型"和"数据库"，自动生成一个迁移脚本。**

**生成完**一定要打开看一眼** —— autogenerate 会漏东西，也会多东西**（比如它认不出列改名，会当成"删一列 + 加一列"，**数据就丢了**）。

```powershell
uv run alembic upgrade head
```
**把数据库升到最新。**

```powershell
uv run alembic downgrade -1
```
**回退一个版本。** 这就是"迁移"比"删库重建"强的地方 —— **有数据的库也能往后退。**

### 提醒：`create_all` 和 Alembic 是两套

**`scripts/init_db.py` 用的是 `Base.metadata.create_all`** —— 它只建"不存在的表"，**不管已有表的结构变化**。

**一旦开始用 Alembic，建表和改表都该走迁移。** `create_all` 只在"全新的空库"上还能用。

| --- | --- | --- |
| **接口文档** | `http://192.168.222.233:8000/docs` | **`http://192.168.222.233/docs`**（不带端口 = 80） |
| **WebSocket** | `ws://192.168.222.233:8000/ws?token=...` | **`ws://192.168.222.233/ws?token=...`** |

**`app` 服务已经**删掉了 `ports`** —— 外面连不上它，只能通过 Nginx。**

### 那三行是给 WebSocket 的

```nginx
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
```

**一个都不能少:**

- **`proxy_http_version 1.1`** —— Nginx 默认用 HTTP/1.0 和后端说话，而 WebSocket 的升级机制是 HTTP/1.1 才有的
- **`Upgrade` + `Connection: upgrade`** —— 成对出现（HTTP/1.1 的规定），把客户端的升级意图转给后端

**还有一行容易漏:**

```nginx
        proxy_read_timeout 3600s;
```

**Nginx 默认"60 秒没数据就断开"，而 WebSocket 常常几十秒不说话 —— 会被当成死连接掐掉。**

### 为什么要 `--proxy-headers`

**加了 Nginx 之后，应用看到的"客户端 IP"变成了 Nginx 容器的内网 IP —— 于是**限流的 key 全撞在一起**（第 12 周那套按 IP 限流会失效）。**

**`compose.yaml` 里 `app` 的 `command` 加了这两项:**

```
      --proxy-headers --forwarded-allow-ips="*"
```

**它让 uvicorn 相信 `X-Forwarded-For` 头，还原真实 IP。**

**⚠️ `--forwarded-allow-ips="*"` 意味着"谁都能伪造 IP"。它安全的前提是:`app` 不对外暴露端口，只有 Nginx 连得上它。**

### 怎么验证它生效了

```bash
docker compose logs app | tail -20
```

**看 uvicorn 自己那行访问日志里的 IP:**

- **`192.168.x.x`**（你电脑的 IP）→ `--proxy-headers` 生效了 ✓
- **`172.x.x.x`**（容器内网 IP）→ 没生效，限流会失效

### `--workers 4` 带来了什么

**应用现在跑 4 个进程。这意味着:**

- **吞吐上去了**
- **第 13 周的连接管理器每进程一份** —— 广播靠 Redis Pub/Sub 才能跨进程（这正是它存在的理由）

### 一个习惯：改完 compose 先验证结构

```bash
docker compose config
```

**它把 compose 文件解析一遍再打印出来。** 缩进错、字段名错、变量没定义 —— **都会在这里报出来，不用等 `up`。**

**（YAML 没有大括号，层级全靠缩进。少两个空格就是一个完全不同的结构 —— 而且看起来还挺像对的。）**

## 十二、压测（Day 16.1 起）

**工具：`locust`，装在**开发依赖**里（`uv add --group dev locust`）—— 它不进应用镜像。**

**脚本：`scripts/locustfile.py`。**

### 跑压测

**在你自己的电脑（PowerShell）：**

```powershell
uv run locust -f scripts/locustfile.py --host http://192.168.222.233 --headless -u 20 -r 5 -t 30s
```

| 参数 | 意思 |
| --- | --- |
| `--host` | 打哪个地址（走 Nginx 的 80） |
| `--headless` | 不开网页界面 |
| `-u 20` | 20 个虚拟用户 |
| `-r 5` | 每秒新增 5 个 |
| `-t 30s` | 跑 30 秒 |

**去掉 `--headless` 会开一个网页界面（`http://localhost:8089`），能实时看曲线。**

### 要看的四个数

| 数 | 含义 |
| --- | --- |
| **吞吐**（Req/s） | 每秒处理多少请求 |
| **P95 延迟** | 95% 的请求在这个时间内完成 —— **平均值会骗人** |
| **错误率** | 非 2xx 的比例 |
| **429 比例** | 被限流挡掉的比例 —— **它不是错误，是"限流在正常工作"** |

### ⚠️ 压测之前要先调大限额

**`RATE_LIMIT_LOGIN` / `RATE_LIMIT_BOOKS` / `RATE_LIMIT_USERS` 默认是 5 / 5 / 10，压测会在几秒内撞上 429。**

**在 **NAS 的** `.env` 里临时调大（**本机的 `.env` 不要动** —— 否则那条"第 6 次 429"的测试会红）：**

```ini
RATE_LIMIT_LOGIN=1000
RATE_LIMIT_BOOKS=100000
RATE_LIMIT_USERS=100000
```

**改完 `docker compose up -d` 重启一下应用（`.env` 变了不会自动生效）。**

### ⚠️ 从本机压测，本机本身可能是瓶颈

**你电脑的 CPU 和家里网络，很可能比 NAS 先到顶。**

**所以当数字不再上升时，你**分不清**是"NAS 到顶"还是"本机发不出更多请求"。**

**想排除这一项:把 locust 放到 NAS 上跑（`docker run` 一个 locust 容器，或者直接在 NAS 上用 uv 装一个），让"压测机"和"被测机"在同一台机器上。**

## 十三、连接池与容量（Day 16.2 起）

**池参数现在也能从 `.env` 调（`core/config.py` 里那三个）。**

### 一个池最多多少连接

```
pool_size + max_overflow        （默认 5 + 10 = 15）
```

### 而应用有 4 个 worker —— 每个 worker 一份池

```
总连接数 = workers × (pool_size + max_overflow)
```

**默认:4 × 15 = 60。**

**⚠️ 这个数必须小于 Postgres 的 `max_connections`（默认 100）。**

**超了之后不是"变慢"，是**所有请求都连不上** —— 整个服务挂掉。**

**调池参数之前，先算一遍这个乘法。**

### 怎么知道池子满了

**① 看日志（最直接）:**

```bash
docker compose logs app | grep -i QueuePool | tail -5
```

**看到这句话就是池子满了:**

```
QueuePool limit of size 5 overflow 10 reached, connection timed out
```

**它把当前配置全写出来了 —— 一看就知道该调哪个。**

**② 直接问 Postgres 有几条连接:**

```bash
docker compose exec pg psql -U postgres -d library -c \
  "SELECT count(*) FROM pg_stat_activity WHERE datname = 'library';"
```

**③ 看 P95:池子不够时，请求会在"拿连接"这一步排队 —— P95 突然抬高，吞吐上不去。**

### 池参数

| 参数 | 默认 | 意思 |
| --- | --- | --- |
| `DB_POOL_SIZE` | 5 | 常驻连接数 |
| `DB_MAX_OVERFLOW` | 10 | 临时能多开几个 |
| `DB_POOL_TIMEOUT` | 30 | 等不到连接最多等多少秒 |

**⚠️ 压测做完记得改回默认值。** 如果为了做实验把池子调到 `1` / `0` 忘了改回来，**你的服务会一直只有 4 条数据库连接。**

## 十四、worker 数与容量观察（Day 16.3 起）

**worker 数现在由 `.env` 里的 `WORKERS` 控制（`compose.yaml` 里写的是 `${WORKERS:-4}`，没有就用 4）。改完要 `docker compose up -d` 重启。**

### 边压边看：`docker stats`

```bash
docker stats
```

**实时刷新每个容器的 CPU / 内存 / 网络。**

**⚠️ 它的 CPU 百分比是"相对**一个核**"的** —— 4 核的机器，`400%` 才是全用满。看到 `100%` 别急着下结论。

**判据:**

| 看到什么 | 结论 |
| --- | --- |
| `app` 的 CPU 很高（接近 `N00%`，N = 核数） | **CPU 是瓶颈** |
| `app` 的 CPU 很低，但 P95 很高 | **瓶颈在别处** —— 数据库、Redis、网络、锁 |
| `pg` 的 CPU 很高 | **数据库是瓶颈** |
| 两边都很闲，但数字上不去 | **瓶颈在你本机的压测工具** |

### 为什么"一个进程只能用满一个核"

**CPython 的 GIL:同一时刻，一个进程里只有一个线程在执行 Python 字节码。**

**所以要更多算力只能多开进程。**

**但请求大部分时间在**等 IO**（查库、查 Redis）—— 等的时候 asyncio 会让位，所以一个进程就能扛很多并发。**

**结论:`--workers` 该给几个，取决于"你的请求里有多少是真的在算"。不量就是在猜。**

**先查核数：**

```bash
nproc
```

### 怎么做对比实验

```ini
# NAS 的 .env
WORKERS=1        # 或者 4
```

```bash
docker compose up -d
```

**然后压一次、记三个数（`Req/s`、`P95`、`app` 的 CPU 峰值），换个 worker 数再来一次。**

**三种结果对应三件事:**

| 结果 | 说明 |
| --- | --- |
| 4 个明显更快 | CPU 是瓶颈，加 worker 有用 |
| 几乎没差别 | 瓶颈不在 CPU |
| **反而更慢** | **worker 超过核数了**，在抢时间片还白占内存 |

### 可选：限制容器 CPU

```yaml
  app:
    deploy:
      resources:
        limits:
          cpus: "2.0"
```

**用 `--workers 4` 去抢 2 个核 —— 吞吐大概率反而下降。这就是"worker 超过核数"的样子。**

## 十五、两个降级演练（Day 16.4 起）

**这两个实验都**不用改代码**，只停服务 / 改 `.env`。**

**⚠️ 做之前先确认限流是 Day 1 调大的状态**（`RATE_LIMIT_BOOKS=100000`）—— **要测缓存，就得让限流保持"不挡"，否则两个变量混在一起。**

### 实验一：停掉 Redis，看缓存值多少钱

```bash
docker compose stop redis
```

**压一次，和没停之前对比 `Req/s` 和 `P95`。**

**看降级日志：**

```bash
docker compose logs app | grep "缓存降级" | tail -5
```

**恢复：**

```bash
docker compose start redis
```

**两个数字的差 = 缓存在这个场景下的价值。**

**⚠️ 记数字的时候要连**条件**一起记**（多少并发、多少数据、什么机器）—— 换了条件结论就不成立。

### 实验二：把限额调回 5，看 429 长什么样

```ini
RATE_LIMIT_BOOKS=5
```

```bash
docker compose up -d
```

**再压一次 —— 失败数会很多，那些全是 429。**

### ⚠️ 一个反直觉的坑

**限流生效之后，`Req/s` 可能**反而比限流关闭时更高**。**

**因为"拒绝一个请求"比"真的去查数据库"快得多** —— 被挡掉的请求压根没碰数据库。

**所以只看吞吐，会得出"限流让系统变快了"这个荒谬结论。**

| 指标 | 只看它会怎样 |
| --- | --- |
| **吞吐** | **429 会让它变好看** |
| **P95** | 只反映"被服务的那些"有多快，被拒绝的不计入 |
| **错误率** | 会把 500 和 429 混在一起 |
| **429 比例** | **单独看它，才知道有多少请求压根没被服务** |

> **先看"有多少请求被真正服务了"，再看"服务得多快"。**

### 实验做完要改回来

```ini
RATE_LIMIT_BOOKS=100000
```

```bash
docker compose up -d
```
