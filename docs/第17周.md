## Day 0：像程序员一样做项目

> **这是动手前要读的第一节。**
> 它不讲技术 —— 讲**工作方式**。
> 前面 16 周教的是"怎么写代码"，这一节教的是"**怎么推进一个项目**"。

### 1. 真实的推进形状：外层直线，内层紧循环

**"做项目"在想象里是一条直线：**

```
需求 → 设计 → 编码 → 测试 → 上线
```

**真实的样子是：外面一圈走直线，里面套着一堆小圈。**

```
想清楚要做什么
   ↓
定表结构、定核心接口
   ↓
写一小块代码  →  跑一次  ←──┐
写一小块代码  →  跑一次      │ 这个圈，一天转几十次
写一小块代码  →  跑一次  ────┘
   ↓
这一块能用了 → 提交 → 划掉 → 下一块
```

**记住这一句就够了：外层按顺序走，内层是"写一点、跑一次"的紧循环。**

### 2. 什么必须提前定死，什么可以边做边改

| 必须先定死 | 可以边做边改 |
| --- | --- |
| **数据模型**（表、字段、关系） | 页面长什么样 |
| **核心接口的输入输出** | 次要接口 |
| **不做什么**（范围边界） | 内部实现细节 |

**为什么数据模型要先定死？因为它最贵。**

> **表结构一改，上面所有代码都得跟着改。而改一句页面文案，五秒钟。**
>
> **先把便宜的拖着，把贵的定死 —— 这是整个工程节奏的底层逻辑。**

### 3. 竖着切，不要横着切

**做的顺序有两种走法。**

**横着切（错的）：**

```
先把所有表建好 → 再把所有模型写完 → 再把所有接口写完 → 最后一起测
```

**结果：做到一半你什么都演示不了。出了问题，也不知道是哪一层。**

**竖着切（对的）：**

```
先打通一条最窄的完整路径：
   一张表 → 它的模型 → 它的仓储 → 它的服务 → 一个接口 → 一个测试
   ↑ 这条通了，你就有了一个「能跑的最小系统」
然后再加第二条、第三条……
```

**为什么竖着切好：**

- **每一步都有东西能看见、能验证**
- **架构的问题会在第一刀就暴露** —— 而不是切了十刀才发现
- **随时能停下来，而且停在一个"完整"的状态**

**（这一条对应的就是阶段 4「搭骨架：一条接口端到端跑通」—— 别跳过它。）**

### 4. 任务清单和提交

**① 清单写在一个文件里，不能记在脑子里。**

`TODOS.md`、GitHub Issues，或者就写在项目 README 里。**关键是它得能被看见。**

**② 每条任务小到"半天到两天能做完"。**

**太大的任务你没法判断"做到哪了"。** "做检索功能"不是一个任务，是三四个任务。

**③ 做完一条，立刻提交，然后划掉。**

> **每一次提交是一个回得去的存档点。**
> **一个提交里塞了三天的活，这个存档点就废了 —— 出了问题你得回退三天。**

**提交信息写"做了什么"，不写"改了什么"。**

- 好：`加上条文的关键词检索`
- 差：`修改 search.py`

**因为三个月后你只看得到信息，看不到代码。**

### 5. 多久跑一次代码

> **几分钟到十几分钟一次。一天几十次。**

| 运行什么 | 多久一次 | 一次多久 |
| --- | --- | --- |
| 跑一下刚写的那一小段 | **写几行就跑** | 秒级 |
| 跑相关的那几个测试 | 每写完一个函数 | 秒级到几十秒 |
| 手动点一下接口（`/docs`） | 每完成一小块 | 一分钟 |
| 跑全套测试 | **提交之前** | 几分钟 |
| 完整跑一遍应用 | 每天收工前 | 几分钟 |

**一条隐藏规律：**

> **你多久跑一次，取决于"跑一次有多贵"。**

- 跑一次要 5 分钟 → **你会本能地不想跑** → 攒着 → 一次炸出 20 个错
- 跑一次要 3 秒 → **你会一直跑**

**—— 这就是第 7 周以来那些测试基础设施的真正动机。**

`pytest`、`fake_redis`、每个测试一个临时数据库、`dependency_overrides` —— **它们不是"为了规范"，是为了让"跑一次"变快。**

> **反馈越快 → 你跑得越勤 → 一次只错一点点 → 修起来就是几秒钟的事。**

**自查信号：**

> **如果你发现自己"有点怕运行代码" —— 那就是该优化反馈速度的信号。**
> **怕，说明它太贵了。**

### 6. 代码怎么跑起来（`__main__` 那件事）

**`if __name__ == "__main__":` 是一句"只有这个文件被直接运行时才执行"的判断。**

```python
if __name__ == "__main__":
    main()
```

- 直接跑这个文件 → `__name__` 是 `"__main__"` → **执行**
- 别人 `import` 它 → `__name__` 是模块名 → **不执行**

**你的项目该不该用：**

| 场景 | 怎么写 |
| --- | --- |
| **Web 应用**（主项目） | **不用** —— 入口是 `uvicorn` |
| **一次性脚本**（`scripts/` 里那些） | **用** |
| 命令行工具 | 用，或者配一个 entry point |

**项目里两种都有，去翻一眼：**

- `src/my_fastapi_project/main.py` —— 没写。它只负责"造出一个 `app` 对象"
- `scripts/redis_check.py` —— 写了。最后一行就是它

**为什么应用不写：**

> **因为"怎么跑"是部署时决定的，不是代码决定的。**

- 开发时：`uvicorn ... --reload`
- 生产：`uvicorn ... --workers 4`
- 容器里：Dockerfile 里的 `CMD`

**写死在 `__main__` 里，这些就都改不了了。**

（更普适的一条：**应用应该是一个"对象"，不是"一个被运行的程序"**。谁来跑它、带什么参数跑，是外面的事。）

### 7. 真实的一天

```
09:00  打开昨天的 TODO，挑最上面一条
09:05  想清楚这条"做完的标志是什么"        ← 最容易跳过的一步
09:10  写一小块
09:15  跑一下 —— 挂了，改
09:20  跑一下 —— 过了
09:25  再写一小块
 ...
10:30  这一条做完了 → 手动点一下接口确认 → 提交 → 划掉
10:35  下一条
 ...
17:30  跑全套测试 → 绿 → 更新 TODO → 提交 → 收工
```

**三件事单独说：**

**① 09:05 那一步最容易被跳过，但它最省时间。**
没有"做完的标志"，你会在一件事上耗一整天，**还不知道做到哪了**。

**② "划掉"和"提交"几乎同时发生。** 不是"这周做完了一起提交"。

**③ 一天的结束不是"写完了一个大功能"，是"测试是绿的、任务划掉了、代码提交了"。**
**哪怕今天只推进了一小格 —— 这三样齐了，今天就是完整的。**

### 8. 卡住了怎么办

**① 卡住超过半小时，换一件事做。**
死磕一小时，往往不如放下去做别的。**这不是意志力问题，是效率问题。**

**② 出错时先读报错，不要猜。**

**读报错的顺序和直觉相反：**

1. **先看最后一行** —— 那是异常类型和消息，信息量最大
2. **往上找第一个属于你自己代码的文件和行号** —— 那才是案发现场（中间那些层是框架的）
3. **看那一行里，哪一部分可能是 `None` / 类型不对 / 名字没定义**

**③ 遇到不会的技术，先用笨办法做出来，记下来，事后再评估。**
第 17 周不许推翻重来 —— **所以"卡住"不等于"停下来学一周"。**

**④ "我不知道" 是可以说的，而且越早说越省时间。**

### 9. 助手怎么带你

**每推进一个小单元，助手的动作顺序是固定的：**

| 步 | 助手做什么 |
| --- | --- |
| 1 | **先说清"做完的标志"** —— 这一步做完，你能看到什么 |
| 2 | **说清起点** —— 现在代码什么样、要动哪几个文件 |
| 3 | **问你："你打算怎么做？"** ← **这一步永远不跳过** |
| 4 | 看你的回答，决定给多少（见下表） |
| 5 | 你写完之后，**审 diff**：挑问题、指出边界情况 |
| 6 | 你跑、绿了、提交、划掉 |

**第 4 步的"给多少"，按状态分五档：**

| 你的状态 | 助手给什么 |
| --- | --- |
| 说得出思路 | **什么都不给**，只看你写 |
| 说不清楚 | **问更小的问题**（不是给答案） |
| 试了但卡住 | **给方向**，不给代码 |
| 完全没头绪 | **给骨架**，留空让你填 |
| 讲了还不会 | **给完整代码 + 逐行注释** |

**脚手架会逐级拆除 —— 但什么时候拆，由你说。**（详见 `docs/教学约定.md` 第七章）

### 10. 你自己怎么写

- **一次只推进一件事。** 不要同时开三块。
- **写几行就跑一次。** 不要攒着。
- **动手前先想"怎么知道它对了"。** 想不出来，说明这件事还没定义清楚。
- **先让它对，再让它整齐。** 不要提前重构 —— 功能还没跑通就整理代码，等于给还没盖好的墙刷漆。
- **出错先读报错，不要猜。**
- **每天收工前 5 分钟：更新 TODO、提交、写下"明天第一件事"。** 这一条能省掉第二天早上的重新进入状态。

### 11. 怎么规划

- **规划的单位是"小单元"，不是"天"。** 判断进度看"做完了几件"，不看"过了几天"。
- **每个小单元必须有"做完的标志"** —— 一个能看见、能验证的东西。
- **优先级：先做"能演示的"**，哪怕是最小的一版。
  > **能演示的东西才能给你反馈；不能演示的东西，你只能在脑子里猜。**
- **想加新功能时：先加进 TODO，不要现在就做。** 这是唯一能挡住范围蔓延的动作。
- **里程碑 = 能给朋友看一次的时刻。**

### 12. 实在做不完时，砍什么

**这个阶段没有截止日期，但现实里总有"来不及了"的时候。真到那一步，按这个顺序砍：**

**能砍的**（砍了不影响"这是个完整项目"）：

- 前端美化 —— **丑没关系，能用就行**
- 次要接口
- 额外的检索策略 —— **先留一种**
- 用户注册 / 权限 —— 如果只有你自己用

**不能砍的**（砍了就不算做完了）：

- **核心路径能从头走通**（问一个问题 → 拿到带出处的回答）
- **能部署，有一个能点开的链接**
- **README 写清楚**（为什么做、怎么跑、踩了什么坑）
- **测试能跑**

> **一个"小而完整"的项目，永远胜过一个"大而半截"的项目。**
> **因为前者能演示，后者只能解释。**

## 选题：结构规范助手

**一句话**：输入"梁的配筋率限值是多少"，给出条文原文和出处，还能接着追问。

**为什么是它**（不是因为它最难，是因为它同时满足三件事）：

| | |
| --- | --- |
| **做得完** | 数据是自己整理的 Markdown，不用抓取、不用清洗 |
| **有深度** | 难点不在 CRUD 上，在下面那六件事上 |
| **和专业咬合** | 建筑结构 + 会写后端 —— **能同时看懂"配筋率"和"向量检索"的人，面试官一天也碰不到一个** |

**目标岗位**：后端开发 + AI 应用开发，**两个都投**。

## 数据准备：条文 Markdown 的格式约定（建议）

**这是开工前唯一需要提前准备的原材料 —— 而它的格式会直接决定后面「切块」怎么做。**

**下面每一条都不是随便定的，各自对应一个后面的需求：**

```markdown
# GB 50010-2010 混凝土结构设计规范

## 8 构造规定

### 8.5 纵向受力钢筋的最小配筋率

**第 8.5.1 条** 钢筋混凝土结构构件中纵向受力钢筋的配筋百分率不应小于表 8.5.1 规定的数值。

1. 受压构件全部纵向钢筋的配筋百分率不应小于 0.6%；
2. 一侧纵向钢筋的配筋百分率不应小于 0.2%。

> 注：本条不适用于……
```

| 格式 | 为什么这么定 |
| --- | --- |
| **一级标题 `#`** | **一部规范一个文件** —— 文件名就是规范号，方便按来源过滤、按来源重建 |
| **二级标题 `##`** | **章** —— 检索结果要能显示"第 8 章" |
| **三级标题 `###`** | **节** —— **切块的第一刀就切在这儿** |
| **加粗的条号** | **引用要精确到"第 8.5.1 条"** —— 所以条号必须能被程序单独认出来 |
| **编号列表** | **款** —— 一条下面的 1、2、3，**切块时绝不能和上一条分开** |
| **引用块 `>`** | 注、条文说明 —— 可以单独切，但要能附回原来那一条 |

**三条硬要求：**

1. **条号必须是一个独立的标记**（比如加粗），**不要混在正文句子里** —— 否则程序分不清"第 8.5.1 条"是引用还是内容。
2. **表格要么转成 Markdown 表格，要么单独标注** —— 规范里大量限值在表格里，**表被切碎 = 答案必错**。
3. **一部规范一个文件，不要合并成一个大文件** —— 合并了就没法按来源过滤，也没法只重建其中一部。

**（这份约定是"建议"不是"规定"。等你自学完 LLM 应用、真正设计切块策略时，可以回来改它。但格式定得越早，返工越少。）**

## 明确不做什么（初稿）

**阶段 1 最重要的产出物不是"要做什么"，是这一节。** 先起草一版，开工时再改。

**不做：**

- **不做多租户 / 团队协作** —— 只有你自己用（或者给同事看一眼）
- **不做条文录入的后台界面** —— **你直接编辑 Markdown 文件**，没有"管理员上传规范"这个功能
- **不做用户注册** —— 需要登录的话，预置几个账号就够
- **不做多轮复杂对话** —— 一次问答 + 追问一轮，够演示了
- **不做移动端 App** —— 浏览器能开就行
- **不做"所有规范"** —— **5–10 部，而且要定死是哪几部**
- **不做答案的自动纠错** —— 出口是"带出处的答案 + 一个评测分数"，不是"保证正确"

**为什么现在就要写这一节：**

> **因为"不做什么"是你唯一能主动控制范围的地方。**
> **功能是长出来的 —— 今天觉得"顺手加个 X 吧"，两周后项目就做不完了。**

## 要留意的几个选型点

**这里不给答案 —— 只列出你自学时要带着看的问题。**

**因为答案会随时间和价钱变，问题不会。**

**① 用哪个大模型？**

- **中文能力够不够？** —— 规范条文是中文，而且是**专业中文**
- **支不支持流式输出？** —— 不支持的话，用户要盯着空白等十几秒
- **一次调用多少钱？** —— 这是你唯一会真的花钱的地方
- **有没有免费额度？够不够把项目做完？**

**② 用哪个 embedding 模型？**

- **中文的相似度算得准不准？** —— 拿你的条文试几条就知道了
- **和大模型是不是同一家？** —— 不同家也行，但要多管一个 key
- **一次调用多少钱？**

**③ 向量放哪？**

- **几千条**：内存里全量比一遍就够，**连数据库都不用**
- 再大：`pgvector` —— **如果第 15 周你最终上了 Postgres，这是个自然选择**
- 更大、或者要更强的检索：专门的向量库

**④ 关键词检索用什么？**

- SQLite 自带的全文搜索？Postgres 的？还是自己写一个简单的？
- **答案取决于第 15 周你最终用哪个数据库**

**别现在就定死。记在这儿 —— 自学 LLM 应用那段时，回来对一遍。**

## 六个真难点（也是面试会被追问的地方）

1. **检索** —— 规范里写的是"纵向受力钢筋的最小配筋百分率"，用户打的是"梁的配筋率限值"。**关键词一个都对不上。** 而纯向量检索又搞不定"第 4.2.3 条"这种精确查询。**混合检索怎么拼，是个真设计。**
2. **分块（chunking）** —— 一条规范下面常常有 1、2、3 款。**按固定字数切，会把一条完整的规定切成两半**，模型只看到半条就会答错 —— 而且答得很自信。
3. **出处** —— 答案是"0.2%"，凭什么是 0.2%？**没有出处的答案等于没有答案。** 而且模型很擅长编一个看起来很像的条号。
4. **幻觉** —— 工程领域最怕编。**"查不到"必须是一个敢说出口的答案。**（这正是第 12 周学的**负缓存**思路：**"没有"本身也是一个值得记住的答案。**）
5. **成本与限流** —— 每次提问都是真金白银。**答案缓存**（第 12 周）+ **按用户限流**（第 12 周）在这里全用上了。
6. **评测** —— 你怎么知道回答是对的？做法是**先手写 50 条"问题 → 标准答案要点"，每次改完跑一遍看命中率**。这是把第 7 周的测试思想搬到了 AI 上。

**六件事里做扎实三件，这个项目在简历上就立住了。**

## 规模策略：先做完整，再灌大

**几千条和上万条，检索方案是同一套。** 真正的断崖不在条数上，在这四件事上 —— **而它们和条数无关，和"你想做到多可靠"有关**：

- 向量要不要**持久化**（每次启动重算一万条，要多久、花多少钱）
- **新规范进来**怎么办（全量重建，还是只处理新增那几条）
- **多个人同时搜**（内存里全量比对的 CPU 扛不扛得住）
- **检索质量**怎么知道好坏

**路径**：先用 5–10 部规范（几千条）把东西**做完整**，再灌到上万条，**看它先在哪儿塌** —— 把"塌在哪儿、为什么"写进项目 README。

**面试时最值钱的一句话，不是"我做过一万条"，而是：**

> **"我知道这套方案到什么规模会开始吃力，以及那时该换什么。"**

## WebSocket 放哪（第 13 周学的不浪费）

**这个题目里 WebSocket 没有天然位置，不硬塞。** 但有一个位置是成立的：**流式输出** —— 模型回答要一个字一个字往外吐，那就是"服务器主动推"。

**不过业界更常用更轻的做法（SSE）。**

**建议**：先用轻的那条把功能做出来；有余力再用 WebSocket 做一遍，**把两者的对比写进项目 README**。

> **"我知道两条路、我选了其中一条、理由是……" —— 这比"我用了所有学过的技术"值钱一百倍。**

## 这一阶段的规则（和前面 16 周完全不同）

1. **我不再给完整代码。** 我给的第一样东西是**问题**，不是答案。
2. **你卡住时，我先问"你打算怎么办"**，再决定给不给提示、给多少。
3. **代码由你写。** 我负责看 diff、挑问题、指出风险和边界情况。
4. **脚手架随进度拆除。** 前期（1–4 阶段）我引导多；中期（5–7 阶段）你为主；后期（8–10 阶段）我只做提示。
   **什么时候拆，由你说。** 我觉得"这个讲过了"不算数。
5. **推进顺序是真实项目的顺序，不是学习顺序。** 先定模型、再定接口、最后写代码；**定下来的尽量不改**。发现前面想错了，**先记下来、评估代价，再决定是改还是绕** —— 不许当场推翻重来。（前面 16 周"今天推翻昨天"是最好的学法，但它不是做项目的样子。）
6. **边写边测，不攒着测。** 每完成一小块，就在浏览器或命令行里验证一次。**先想清楚"怎么知道它对了"，再动手写。**
7. **讲解写在代码注释里，不是写在代码外面。** 每一行代码下面跟一行注释，宁可多不可少。具体规则见 `docs/教学约定.md` 第七章。

## 提前记下的三个风险

- **范围失控**：第一次做项目最常见的失败不是技术卡住，是"想做的太多 → 做不完 → 停在那里"。所以阶段 1 的重点不是"想做什么"，是**决定不做什么**。
- **永远不上场**：把"再学一点"当成推迟的理由。**这个风险在你身上是加倍的** —— 因为第 17 周明确排在"很久以后"。**给自己定一个具体的开工条件**（就是上面那份清单），或者干脆定一个日期。**别让它变成一个永远在未来的事。**
- **接不上**：中间隔了那么久，回来时手生了，当初为什么这么想也忘了。**缓解办法就是这份文档** —— 方向、难点、下手顺序都落在纸上了。另外，**每学完一块（SQL、LLM）就回来翻一眼**，让它一直活着。

## 附：选题的评判标准（以后换题用）

**不是"哪个想法最酷"，是"哪个做得完"。**

**以后想换题、或者做第二个项目时，拿这五个问题过一遍：**

| 问题 | 为什么问它 |
| --- | --- |
| **谁是用户？** | 答不上来 = 还没想清楚，不是"学得不够" |
| **他现在的麻烦是什么？** | 现在拿 Excel / 微信群 / 纸笔是怎么凑合的 |
| **数据从哪来？** | **最容易低估的一项** —— 手动录？抓取？从别的系统导？ |
| **最小可用版本是什么？** | 砍到只剩一个核心动作，它还有用吗？ |
| **讲 5 分钟时，亮点是哪一句？** | 说不出这一句，项目就还没有灵魂 |

**"数据从哪来"要单独标出来。** 它是第一次做项目最常见的隐形杀手：功能都想好了，动手才发现数据要一行行手录，或者抓下来还要清洗半天 —— **项目就卡死在第一周，而且卡住的还不是编程。**

**顺带记一下被淘汰的候选，以及为什么：**

- **图纸 / 审图意见台账** —— 本来也是好选择（数据自产、量小、正好用上 WebSocket）。输给规范助手的地方在于**面试时讲不出"AI 应用"这一块**，而目标岗位是两个都投。
- **结构计算书生成器** —— **不推荐**。不是技术难，是"正确"的定义太难：算错一个数就是工程事故，你会不自觉去追"像专业软件一样可靠"，那是个无底洞。**第一次做项目，要选一个"做错了只是不好用"的题目。**
